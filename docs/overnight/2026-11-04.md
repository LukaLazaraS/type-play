## Answers (decided by Luka through HQ; no questions tonight)

- Code-drawn 2D art stays. Fix = draw each look once, reuse for every copy (flyweight); animate the picture (move, turn,
  scale, a few frames drawn at start); redraw only when a look really changes; live drawing every frame only for a few
  things (player, a health bar); first drawing behind the loading screen.
- Fast by how the code is written, at every level / point of progress / condition: a frame's cost must not grow with
  play time (shared looks, pools, caps, nearby-only checks, targets picked a few times a second). Plus a short automatic

  the agent like a failed test. Must work for a 2-hour game too.

  screen.
- Research first, with sources; write it up in docs/research/; turn it into the game agent's rules.

- Start-freeze prototype (WebGL probe in web.mjs, cold profile, 4x CPU, SwiftShader): show-runner-polished and
  show-3d-polished each link 1 shader program after play starts; all showcase games show ~1 s at the tap (level build
  + SwiftShader read-back). 3D frame times in SwiftShader are meaningless (median 224 ms), so the budget is the
  number of programs linked after play starts; frame times are reported, not failed (seen: one run 49 ms worst, the
  same probe next run 1019 ms: shared-PC noise).
- `lib/looks.gd` (shared looks, flyweight) + `lib/warmup.gd` tested in the browser: 300 sprites fine; with the
  warm-up 0 programs after play starts, without it 1 (the first particle burst, 143 ms after the tap). A transparent
  SubViewport stores premultiplied colour (50% red read back as 0.5,0,0,0.5: muddy); fixed with a second pass that
  un-premultiplies (`blend_disabled` shader), read back 1.0,0,0,0.5, screenshot correct. No GPU read-back at all.
- Budgets (calibrated): the stress test's frame budget is 4.0 ms of game code at bench 4.0 ms (scaled by the
