## The task (HQ's brief, Luka's answers)

An Assets section in the game builder. Luka: a page, section or tab where the player sees every asset their game uses,
so they can look at it, screenshot it and ask for a change; maybe edit it there; maybe send it to the chat. A very big
feature: plan it well, good UX and UI practice, no hurry. Max effort.

1. Plan first (`docs/design/assets.md`): what counts as an asset, the player's journeys (find the boss picture, ask to
   change it; download the music; see what the AI used), the screens on phone and computer, the data and the API, the
   costs, what ships tonight and what is a proposal. Competitors (Rosebud AI, Lovable, Bolt, Replit, Roblox and Unity
   asset browsers), with sources.
2. Find what games really contain: image files, the 3D library's models, sounds (made in code today), fonts, art drawn in
   code. The speed night's Looks (each code-drawn look made once and reused): can they be listed and exported as
   pictures at build time?
3. HQ's default scope: an Assets tab next to Chat and Play on the game page: every picture, 3D model, sound and font the
   version on screen uses, with a preview (thumbnail; a still or a turnable view for 3D; a play button for sounds), a
   plain name and where it is used; code-drawn looks shown as pictures made at build time (a manifest of the build,
   nothing drawn per view); Download each; Change it puts the asset into the chat box as an attachment (image attach's
   own way) with a starter text naming it. Replace by upload: a proposal only. Empty state, loading, errors. Private to

4. Older builds without a manifest: what they show, and whether a rebuild or a background job fills them, cheapest first.
5. Shared pieces in `apps/web/src/components/ui`, the design system; 320, 390, 1440 px; keyboard and screen reader; big

## Decisions (taken tonight, the standard way; Luka can change any)

- **Where the tab is:** phones get a third tab (Chat / Play / Assets); computers get a Play / Assets switch at the start
  of the game's bar, with the chat always beside it. That is where Rosebud (Preview / Assets / Code) and Lovable
  (Preview / Files / Code) put it, and it lets Change it land in the chat box in place, several assets in one message.
  The game keeps running behind the list (its frame stays mounted, as on the phone's Chat tab).
- **Which version:** the game's current version (its newest build, the one the page names), so a change sent from the
  list shows its new art there when it is done.
- **Code-drawn art and sounds are captured at build time** (`packages/agent/tools/capture.mjs` + `capture.gd`): a copy
  of the game with a capture autoload, played once in the hidden browser after the last good commit, in parallel with
  the closing AI calls. Shared looks are read back from lib/looks.gd's pictures (the GPU read-back happens in the copy
  only), sounds made in code are found by walking the game's nodes and their variables, and each 3D model gets a still
  from the game's own renderer. Never fails a build.
- **The server lists the files itself** at publish (pictures, models, sounds, fonts, where each is used) and adds the
  captured items; the same code lists an older version's files. Stored per game, content-addressed (a model used by
  50 versions is kept once), deleted with the game. No database table: one manifest file per build.
- **Names:** looks get an optional plain name (a 4th argument to Looks.add, one line in rules/FAST.md); without one the
  name comes from the key and the drawing function. Change it's starter sentence names the asset and its handle in the
  code, so the AI changes the right thing.
- **Change it** goes through image attach's own way in: the picture is handed to the box's tray (`add(files)`) as if
  the player had dropped it, with the starter sentence.
- **Turnable 3D view:** Google's `<model-viewer>` (the web standard for glTF), loaded only when a model is opened, from
  a self-contained GLB the server makes at import.
