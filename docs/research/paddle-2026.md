# Paddle Billing for TypePlay: research facts, 2026-10-18

Four read-only research passes on the night of 2026-10-17/18 (Paddle's developer docs, legal and help pages, Paddle's Node SDK
source, NestJS, PostgreSQL and Prisma docs, EUR-Lex / CJEU, legislation.gov.uk, gov.uk, the California statute, law-firm notes)
plus this repo. They feed `docs/payments-design.md`, which cites the keys in brackets; the keys are listed with their URLs and
dates at the end. Tags: **FACT** = read on the page; **ESTIMATE** = inferred, method given. Paddle's developer pages carry no
last-updated date, so they count as "accessed 2026-10-18" unless a changelog date is given.

## 1. Environments, keys, go-live

- FACT [R-E1]: the sandbox is a separate account (sandbox-vendors.paddle.com) with the same features and APIs but separate data, keys, client tokens, destinations, products, prices and customers. Base URLs `https://sandbox-api.paddle.com` / `https://api.paddle.com`; a key used against the wrong one gets `forbidden`.
- FACT [R-E1]: sandbox vs live: no website approval vs required; default payment link on any domain vs an approved one; test cards only vs real cards; a "Test Mode" watermark; refunds auto-approved every 10 minutes vs Paddle approval for most; webhook retries 3 within 15 min vs 60 within 3 days; no payouts; customer emails go only to addresses on the account's registered domain, every other address is forwarded to the account's main email; no payment retries (dunning) in sandbox.
- FACT [R-E3]: test cards (any name, any future expiry, security code such as 100): `4242 4242 4242 4242` succeeds; `4000 0038 0000 0446` 3DS challenge; `4000 0000 0000 0002` declined; `4000 0027 6000 3184` first payment succeeds, later ones decline; `4000 0566 5566 5556` Visa debit. Test cards never work live and live cards never work in sandbox.
- FACT [R-E2]: API keys use `Authorization: Bearer`, are created at Paddle > My account > Settings > Authentication, prefixed `pdl_sdbx_apikey_` / `pdl_live_apikey_`, 69 characters matching `^pdl_(live|sdbx)_apikey_[a-z\d]{26}_[a-zA-Z\d]{22}_[a-zA-Z\d]{3}$`, shown once; permissions are set at creation (a missing one → 403 `forbidden`); expiry default 90 days, at most 1 year, no revalidation; webhooks `api_key.expiring` (7 days before) and `api_key.expired`; keys found in public GitHub repos are revoked; server-side only (the API's CORS header blocks browsers).
- FACT [R-E2]: client-side tokens are a separate credential for Paddle.js, safe in frontend code (open checkouts, price and transaction previews), prefixed `test_` / `live_`, made on the same screen.
- FACT [R-E5]: the `Paddle-Version` header is optional (current version 1); without it the account's default applies (the version current at sign-up, never changed by Paddle). Destinations carry their own API version.
- FACT [R-C1]: the default payment link (Paddle > Checkout > Checkout configuration) must be set per environment before any transaction ("You must set your default payment link to start selling"); a page on an approved site that includes Paddle.js; `https://localhost/` is suggested for sandbox; a transaction's `checkout.url` = that link + `?_ptxn=txn_…`, which opens the checkout on load.
- FACT [R-E6]: go-live checklist: the default payment link on the verified domain, payment methods, the sales tax setting, balance currency, dunning, payout details; recreate products, prices and discounts in live; "request approval for any taxable categories you need beyond Standard Digital Goods"; switch the base URL, key and client token; remove `Paddle.Environment.set("sandbox")`; replace sandbox price ids; new notification destinations; allowlist Paddle's IPs; verify signatures; rotate keys.
- FACT [R-E4]: Paddle's API has no idempotency keys; the SDK page says to list or get the entity before retrying a create. The Node SDK `@paddle/paddle-node-sdk` is at 3.10.0, Node ≥ 20, zero runtime dependencies.
- FACT [R-L7]: Paddle serves software businesses anywhere except a list of unsupported countries (Afghanistan, Belarus, Cuba, Iran, Iraq, Libya, Myanmar, North Korea, Russia, Syria, Venezuela, Yemen, Zimbabwe and others); Georgia is not on it. ESTIMATE: nothing on those pages says sole traders skip documents; expect an identity check and a name match with the IE registration (`docs/payments.md` 10-14 found business verification "not required for individuals or sole traders").

## 2. Catalog: products, prices, tax

- FACT [R-C4]: `POST /products`: `name` (1-200), `tax_category` required and "must be enabled on your Paddle account" (standard, saas, digital-goods, ebooks, implementation-services, …), `description` ≤ 2048, `type` standard | custom, `image_url`, `custom_data`; id `pro_…`; no delete, archive instead.
- FACT, conflicting [R-C3]: the create-products guide says `standard` and `saas` "are available on all accounts by default"; the go-live checklist says to request approval for categories beyond Standard Digital Goods; a Classic-era help article says non-standard categories wait for approval and warns that SaaS "has specific criteria for taxation".
- FACT [R-C2]: `POST /prices`: `description` (internal, required), `name` (shown at checkout and on invoices), `product_id`, `unit_price { amount, currency_code }` with the amount a string in the lowest unit ("10 USD = 1000"), `billing_cycle { interval day|week|month|year, frequency }` or null = one-time, `trial_period`, `tax_mode` account_setting | external (exclusive of tax) | internal (inclusive) | location, `unit_price_overrides` (≤ 250), `quantity { minimum 1, maximum 100 }`, `custom_data`; id `pri_…`; a price belongs to one product; archive, no delete. 33 currencies including USD, EUR, GBP, INR, JPY.
- FACT [R-C8] (2025): the `location` tax mode (exclusive or inclusive by the buyer's country) can be the account default ("Automatic based on location"); existing prices keep their mode.
- FACT [R-C9]: Paddle's AI-companies guide: "sell prepaid credits as one-time products and track the balance in your app"; plans with an included quota are supported; overages as one-time or non-catalog items; native usage billing is an early-access beta.
- ESTIMATE (design, from the above and `docs/pricing.md`): 5 products (Medium, High, Ultra, Ultra+, Credit pack), monthly USD prices "2000" / "5000" / "10000" / "20000" and a one-time "1000", all `tax_mode: external`, each price's `custom_data { plan, credits }` so a webhook maps a price to a grant without a hard-coded table; price ids per environment in config.
- FACT [R-C10]: `POST /pricing-preview` and `POST /transactions/preview` (permission `transaction.read`) return totals with tax for a location (`customer_ip_address`, `address { country_code, postal_code }`, or customer / address ids); `Paddle.PricePreview()` / `Paddle.TransactionPreview()` are the Paddle.js forms and detect the location by IP. Whether a client token may call the transaction preview is unclear (the authentication page says yes, the endpoint lists `transaction.read`).

## 3. Checkout: Paddle.js, customers, transactions, custom data, consent boxes

- FACT [R-J1]: Paddle.js loads from `https://cdn.paddle.com/paddle/v2/paddle.js`; `Paddle.Environment.set("sandbox")` only for sandbox; `Paddle.Initialize({ token, eventCallback, checkout: { settings }, pwCustomer })` once per page (`Paddle.Update()` later); `pwCustomer` is for Retain (live only). `Paddle.Checkout.open()`: `items [{ priceId, quantity }]` (recurring items share one billing interval) or `transactionId` ("Paddle uses the customer, items and pricing from the existing transaction"); `customer { id | email }` (never both) with optional `address` / `business`; `customData` (valid JSON, at least one key; held on the transaction, copied to the subscription); `discountCode | discountId`; `customerAuthToken`; `savedPaymentMethodId`. Settings: `displayMode` overlay | inline, `variant` multi-page | one-page | express, `theme` light | dark, `locale` (19 incl. en, de, fr, es, ja), `successUrl` (http/https), `allowLogout` ("whether the user can change their email once on the checkout", default true), `allowDiscountRemoval`, `showAddDiscounts`, `showAddTaxId`, `allowedPaymentMethods`, `frameTarget`, `frameInitialHeight` (450 recommended), `frameStyle` (min-width ≥ 286 px). One checkout may mix recurring and one-time prices; events expose `totals` and `recurring_totals`.
- FACT [R-J4]: prefill: customer, address and business ids replace the other fields; the first page is skipped when country, email and postal code (where required) are prefilled or a customer id plus an address id is given; invalid optional data still opens the checkout and emits `checkout.warning`.
- FACT [R-J2]: checkout events: loaded, updated, completed, closed, customer.created / updated / removed, payment.initiated / selected / failed / error, error, warning, items.updated / removed, discount.applied / removed, upsell.canceled. `checkout.completed`: `data.id` is the checkout id (`che_`), `data.transaction_id` the `txn_`; `data.customer { id, email, address }`, `data.items[]`, `data.totals` / `recurring_totals`, `data.currency_code`, `data.custom_data`, `data.payment.method_details { type, card { type, last4, expiry_month, expiry_year } }`. A UI event: fulfil from webhooks.
- FACT [R-C6]: `POST /transactions { items, customer_id, address_id, custom_data, collection_mode: "automatic" }`; `draft` until the required fields exist ("typically the first stage of a checkout before customer details are captured"), `ready` with items, customer and address; `checkout.url` is returned for automatic collection; `allowLogout: false` stops the buyer changing details. Statuses: draft, ready, billed, paid, completed (paid and processed), canceled, past_due. Origins: api, web, subscription_recurring (renewal), subscription_update (plan change), subscription_charge (one-time charge), subscription_payment_method_change. `billing_period` is set on renewals; `subscription_id` and `invoice_number` are added during completion; `details.line_items[].id` (`txnitm_`, used for adjustments), `.proration { rate, billing_period }` (null unless from a subscription change), `.totals { subtotal, discount, tax, total }`; `details.totals { subtotal, discount, tax, total (after discount and tax), credit, credit_to_balance, balance, grand_total, fee, earnings (null until completed) }`; `payments[] { status captured | error | action_required …, error_code, method_details, captured_at }`.
- FACT [R-C7]: `custom_data` is key-value JSON (nesting discouraged); checkout `customData` is held on the transaction; a transaction that creates a subscription copies it there; subscription custom data is copied to every later transaction (renewals, upgrades, downgrades, one-time charges); visible in transaction webhooks; editable until billed / completed (transactions) or by PATCH (subscriptions); no size limit documented.
- FACT [R-C5]: `POST /customers { email (required, unique), name, custom_data, locale }` → `ctm_…`; a duplicate email returns HTTP 409 `customer_already_exists` with the existing id in the `detail` string; no delete (archive). At checkout Paddle reuses an existing customer with the same email. Paddle's mobile guide recommends creating the customer server-side and storing the id on the user. Addresses (`add_`) need `country_code`, and `postal_code` for some countries (US, UK). Several active subscriptions per customer are allowed.
- FACT [R-C11]: changing a customer or address later does not change billed or completed transactions; `POST /transactions/{id}/revise` changes the name, business, tax id and address (not the country) once, and Paddle emails the revised invoice.
- FACT [R-J3] (changelog 2025-07-01): Paddle Checkout shows a consent checkbox to California buyers of auto-renewing subscriptions ("I agree to be charged $X on <date>, then $X automatically every month. I can cancel anytime using the link in my receipt email from Paddle."), above the pay button (overlay) or before the payment methods (inline), on every checkout variant, with no implementation; it can change the inline frame height. Paddle's update of 2025-07-01 extended a recurring-billing checkbox to the rest of the US from 2025-07-14 ("There is nothing you need to do"); the FTC's wider rule was blocked in court (2025-07-08). Since 2025-09-16 buyers must tick to save a payment method; since 2026-03-19 South Korea renewal consent.
- FACT [R-J5]: saved payment methods only on the one-page checkout, with a customer auth token from `POST /customers/{id}/auth-token` (valid 30 minutes) and the dashboard switch "Allow saved cards" (off by default); a subscription's card on file is not a saved method unless the buyer opted in.
- FACT, by absence [R-L8]: no Paddle developer page describes an EU "immediate performance" consent box; Paddle's buyer terms carry a digital-content waiver ("where a product is digital content which is immediately made available … you consent to immediate performance … and acknowledge that you will lose your right of withdrawal", 2022 text). ESTIMATE: our own tick box on typeplay.app before `Paddle.Checkout.open()` is the only express request on record.

## 4. Subscriptions

- FACT [R-S1]: the entity: `status` active | canceled | past_due | paused | trialing; `customer_id`, `address_id`, `currency_code`, `started_at`, `first_billed_at`, `next_billed_at`, `paused_at`, `canceled_at`, `collection_mode`, `current_billing_period { starts_at, ends_at }` (null when paused or canceled), `billing_cycle`, `scheduled_change { action cancel | pause | resume, effective_at, resume_at }`, `management_urls { update_payment_method, cancel, view_subscription }` (customer-portal links since 2025-04-28; buyers log in by email), `items[] { status, quantity, price, product, previously_billed_at, next_billed_at }`, `custom_data`. `subscription.created` alone carries `transaction_id`; `subscription.updated` is the catch-all (renewals, item changes, scheduled changes, status transitions) and also fires right after `.activated` / `.canceled`; every subscription event carries the full entity (minus `management_urls`). `subscription.paused` leaves the period and `next_billed_at` null with items inactive; `subscription.resumed` bills at once with a fresh period; `subscription.activated` fires when a subscription becomes active (also after a recovered payment and on resume).
- FACT [R-S8]: Paddle's provisioning guide: save the customer and subscription ids on `subscription.created`; refresh on `subscription.updated` ("you don't need to listen for separate events for renewals, upgrades or downgrades"); keep access on `past_due`; revoke on `canceled` (keep access until a scheduled change takes effect); gate self-serve plan changes while `scheduled_change` is set; dedupe on `event_id`, compare `occurred_at`; run a periodic reconciliation.
- FACT [R-S2] (scheduled-change rule changelog 2025-04-14): `PATCH /subscriptions/{id}`: the complete `items[] { price_id, quantity }` (omitted items are removed; only recurring prices); `proration_billing_mode` is required when items change: `prorated_immediately` (prorate on the current cycle, bill now), `prorated_next_billing_period` (prorate now, bill at the renewal), `full_immediately` (the full amount now), `full_next_billing_period` (the full amount at the next renewal), `do_not_bill` (not billed for the prorated or the full amount); `on_payment_failure` `prevent_change` (default) | `apply_change`; `scheduled_change` may only be set to null. No change within 30 minutes of the next billing date; `past_due` subscriptions can't be changed; one billing interval; a subscription with a scheduled pause or cancel may only use `full_immediately`, `prorated_immediately` or `do_not_bill`. Events: `subscription.updated`, plus `transaction.created` when the mode bills. There is no way to schedule an item change for a future date.
- FACT [R-S3]: proration is calculated to the minute; the rate is on `details.line_items[].proration` of the resulting transaction; since 2024 a prorated change is one transaction with negative lines for unused time; an excess goes to a per-currency customer credit balance (`credit_to_balance`), "created automatically by Paddle" and applied to future transactions; you cannot add credit by hand.
- ESTIMATE [R-S2's example response and a RevenueCat community report]: with the `*_next_billing_period` and `do_not_bill` modes the subscription's items change at once and only the money is deferred. So "downgrade at the next renewal" (`docs/pricing.md`) is ours to keep: `do_not_bill` now, our `pendingPlan` until the renewal's `transaction.completed` carries the new price; to confirm with the preview endpoint and one sandbox renewal.
- FACT [R-S4]: `PATCH /subscriptions/{id}/preview` returns `immediate_transaction` (non-null only for `prorated_immediately` / `full_immediately`), `next_transaction` (null if a cancel or pause is scheduled; includes charges for the next-period modes), `recurring_transaction_details`, `update_summary { credit, charge, result { action credit | charge, amount } }`; amounts are strings in the lowest unit.
- FACT [R-S5]: `POST /subscriptions/{id}/cancel` with `effective_from` `next_billing_period` (default; sets `scheduled_change { cancel, effective_at }`, `next_billed_at` null, status stays active; `subscription.updated` now, `subscription.canceled` on the date) or `immediately`; undo with `PATCH { scheduled_change: null }`; no cancel or pause within 30 minutes of the billing date; paused subscriptions only cancel immediately; canceled subscriptions can't be reinstated; nothing is said about automatic refunds.
- FACT [R-S7] (changelog 2025-01-09): default payment recovery on live accounts: a failed renewal sets `past_due`, up to seven retries over 30 days, then automatic cancel (configurable: window, pause vs cancel; not the retry timing); `transaction.payment_failed` carries `payments[].error_code` (declined, expired_card, not_enough_balance, fraud, psp_error, …) and can repeat for every failed retry; no retries in sandbox.
- FACT [R-S6]: `POST /subscriptions/{id}/charge { effective_from immediately | next_billing_period, items (one-time prices only), on_payment_failure }`: immediately = a transaction collected now with the subscription's payment method, origin `subscription_charge`; never added to `items`; the same 30-minute and past_due limits; preview at `…/charge/preview`.
- FACT [R-P1] (view_subscription changelog 2026-09-28): `POST /customers/{id}/portal-sessions { subscription_ids ≤ 25 }` → `urls.general.overview`, `urls.subscriptions[] { cancel_subscription, update_subscription_payment_method, view_subscription }`; "temporary and shouldn't be cached", no lifetime published. The portal (on by default, magic-link sign-in) shows payments and invoices, updates the payment method and cancels (Retain's cancellation flow first, in the portal since 2026-01-09); "for compliance, you must offer a way for customers to cancel". Self-serve plan changes in the portal are early access (product collections; upgrades `prorated_immediately`, downgrades applied at once with `prorated_next_billing_period`).

## 5. Refunds, adjustments, chargebacks, fees

- FACT [R-A1] (tax-exclusive refunds changelog 2025-03; full-type adjustments 2024-12): `POST /adjustments { action: "refund", type: "full" | "partial" (default; needs items), transaction_id, items: [{ item_id: "txnitm_…", type: "full" | "partial", amount }], reason (required), tax_mode: "internal" (amounts include tax, default) | "external" (Paddle adds the tax) }`; only for `completed` transactions; "you can't create an adjustment for a transaction that has a refund that's pending approval"; most live refunds start `pending_approval`, then `approved` or `rejected` (`adjustment.updated`); some are created `approved` at once and never emit `.updated`, so handle both; credits are created approved; `reversed` when a reverse adjustment is made. Adjustments are "financial records" that can't be changed or deleted. Response totals include `fee`, `earnings`, `retained_fee`; `payout_totals.chargeback_fee` on chargebacks. Actions a handler sees: refund, credit, chargeback, chargeback_warning, chargeback_reverse, chargeback_warning_reverse, credit_reverse.
- FACT [R-A3] (changelog 2024-06-28): live refunds are approved automatically when the account is approved and active, the amount is ≤ 400 USD (or equivalent) and below the seller's balance, and the payment was not a bank transfer; sandbox approves every ten minutes.
- FACT [R-A5]: card payments are refundable only within 120 days, PayPal 179; card refunds take 3-5 working days, PayPal about 48 h; a refund reduces a credit balance created by that transaction.
- FACT [R-A6] (changelog 2025-09-22): `retained_fee` = "Paddle fees retained for this adjustment" (gateway costs); the help centre says Paddle keeps the original processing fee. ESTIMATE: `docs/pricing.md` assumes the whole 5% + $0.50 is kept; read a sandbox refund's `payout_totals.retained_fee`.
- FACT [R-A4]: the chargeback fee is 20 USD/GBP/EUR (40 CAD/AUD), not returned even when Paddle wins; pre-chargeback alerts are refunded in full and still carry the fee; Paddle's Dispute Defense contests chargebacks itself and accepts no seller evidence; acceptable rate "below 0.65% of transaction volume" (the handbook says above 0.75% is unacceptable); chargebacks can come up to 120 days after delivery.
- FACT [R-L9]: Paddle's fee is 5% + 50¢ per checkout transaction, no monthly fee; products under $10 need bespoke pricing.
- FACT [R-L6] (MSA, last updated 2026-10-06): §10.1 the seller must not refund buyers directly, refunds go through Paddle; §10.2 Paddle may cancel and refund in full if the buyer asks within 14 days of a one-off purchase or the last renewal and Paddle finds it appropriate, or on error, fraud or chargeback risk; §10.3 excessive refund or chargeback rates allow suspension or termination; §10.4 the seller owes the refund plus fees and up to 20 USD/GBP/EUR per chargeback or alert; reserves may be held up to six months after termination; §6.2 the seller must promptly help with buyer complaints.
- ESTIMATE (arithmetic on `docs/pricing.md`): a chargeback on Medium costs the $20 sale + the $20 fee + up to $6 of AI; 0.65% of volume at $20 a sale is about one chargeback per 150 sales.

## 6. Webhooks

- FACT [R-W1]: every webhook is a POST with `{ event_id "evt_…", event_type, occurred_at (RFC 3339), notification_id "ntf_…", data }`; one event to two destinations = one `event_id`, two `notification_id`s. At-least-once delivery ("use event_id to deduplicate"); order not guaranteed ("use occurred_at rather than arrival time"); respond 200 within five seconds, before processing; retries with exponential backoff: sandbox 3 in 15 min, live 60 in 3 days (20 in the first hour, 47 in the first day); then status `failed`. Statuses: not_attempted, needs_retry, delivered, failed. IPs to allowlist: sandbox 34.194.127.46, 54.234.237.108, 3.208.120.145, 44.226.236.210, 44.241.183.62, 100.20.172.113; live 34.232.58.13, 34.195.105.136, 34.237.3.244, 35.155.119.135, 52.11.166.252, 34.212.5.7; "configure your firewall to bypass bot checks on webhook endpoint paths" and match `Paddle` as the user agent. Content-Type and User-Agent are not documented; simulator logs show `Paddle-Version: 1`.
- FACT [R-W2]: `Paddle-Signature: ts=<unix seconds>;h1=<hex>`; the signed payload is `<ts>:<raw body>`; `h1` = HMAC-SHA256 with the destination's secret, hex; "signatures contain at least one h1", more during a secret rotation; don't transform the raw body (Express: `express.raw`); Paddle's example uses `timingSafeEqual` and an optional 5-second age check; the Node SDK hard-codes 5 s, rejects old signatures only, compares with `===`, takes the last `ts` / `h1` when several appear, and `paddle.webhooks.unmarshal(rawBody, secret, header)` throws on a bad signature. The secret is per destination, `^pdl_ntfset_[a-zA-Z0-9]{26}_[a-zA-Z0-9+/=]{32}$` (70 chars; the last part is base64, so it can hold `+`, `/`, `=`: seen on our sandbox destination 2026-10-25), returned at creation and, per the signature page, readable later in the dashboard or by `GET /notification-settings/{id}` `endpoint_secret_key` (the destinations page says it can't be retrieved again: check the dashboard). No rotation procedure is documented.
- ESTIMATE [R-W6, Paddle's own agent skill]: retries re-sign with a fresh `ts`, so a tolerance wider than 5 s costs nothing while `event_id` dedupe stands.
- FACT [R-W4] (changelog 2023-06-20): `POST /notifications/{id}/replay` (status delivered or failed, origin event only) creates a new notification with the same `event_id`; notifications older than 90 days aren't retained. Dashboard: Paddle > Events > Notifications > the destination's menu > View logs; a Replay button for real events is reported by third parties only. ESTIMATE: a handler that dedupes purely on `event_id` ignores replays; store the status and let a replay re-queue a failed row.
- ESTIMATE [R-W7, from the notification entity's `times_attempted`, `retry_at`, `last_attempt_at`]: automatic retries keep the same `notification_id`; only replays mint a new one.
- FACT [R-W8]: destinations: Paddle > Events > Notifications > New destination: description, type webhook | email, URL, API version, usage type (`traffic_source` platform | simulation | all), the events; `POST /notification-settings { description, type, destination, subscribed_events, api_version, include_sensitive_fields, traffic_source }`; at most 10 active; deactivating keeps logs. Event types include transaction.{billed, canceled, completed, created, paid, past_due, payment_failed, ready, revised, updated}, subscription.{activated, canceled, created, imported, past_due, paused, resumed, trialing, updated}, adjustment.{created, updated}, customer.*, address.*, payment_method.*, payout.*.
- FACT [R-W5]: the simulator (Paddle > Events > Simulations) sends single events or scenarios to destinations whose usage type allows simulations; simulated ids are `ntfsimevt_…`; payloads are editable; works in sandbox and live; the page says signatures can be verified and the key revealed (Hookdeck says simulations are signed with the destination's key: to confirm). Scenario "Subscription created": transaction.created → customer.created → address.created → transaction.updated → transaction.ready → transaction.updated → transaction.paid → subscription.created → subscription.activated → transaction.updated ×2 → transaction.completed (→ payment_method.saved). "Renewed": subscription.updated → transaction.created (subscription_recurring) → billed → updated → paid → updated → completed; failed: … payment_failed → transaction.past_due → subscription.updated → subscription.past_due → (dunning exhausted) subscription.canceled | paused. "Canceled": subscription.updated (scheduled) → at effective_at subscription.updated (canceled) → subscription.canceled. "Paused" and "Resumed" alike (a resume bills at once).
- FACT [R-T1]: `transaction.completed` fires when the status becomes `completed` (payment captured and processing done: payment details logged, fee and earnings added, the subscription created and `subscription_id` + invoice fields added for automatically-collected transactions); `transaction.paid` fires earlier and may lack `subscription_id` and `invoice_number`; `transaction.updated` fires three or four times per purchase (noise); fee and earnings are null until completed.
- FACT [R-A2]: `adjustment.created` and `adjustment.updated` both carry the entity (`id adj_`, action, type, status, transaction_id, subscription_id, customer_id, items[] { item_id txnitm_, type, amount }, totals { subtotal, tax, total, fee, earnings }, payout_totals); the example shows amount "100" → subtotal "92", tax "8", total "100", fee "5", earnings "87" (ESTIMATE: amounts are positive strings in the lowest unit; no rule is stated).
- FACT [R-N1]: NestJS: `NestFactory.create(AppModule, { rawBody: true })` and `req.rawBody` (`RawBodyRequest<Request>`), only with the built-in body parser on; `app.useBodyParser('json', { limit })` respects rawBody; Express's json limit is 100 kb by default.
- FACT [R-DB1]: PostgreSQL's default isolation is Read Committed (two SELECTs in one transaction can see different data); `SELECT … FOR UPDATE` blocks other writers until the transaction ends; Serializable needs a retry on SQLSTATE 40001. Prisma 7 interactive transactions: `maxWait` 2 s and `timeout` 5 s by default, optional `isolationLevel`, P2034 on a serialization conflict.

## 7. Emails Paddle sends (as merchant of record; cannot be turned off)

- FACT [R-M1]: a receipt with a PDF invoice on every completed transaction ("Your receipt from <Company>"); subscription confirmation, cancel request, canceled, billing-date changed, price changed, pause / resume, scheduled-change canceled; full and partial refund emails; trial confirmations; checkout recovery; four dunning emails after a failed payment; localized in 16 languages; a redesign is rolling out. Receipts cannot carry seller text (the product entity has only name, description, image). Buyer emails to Paddle support are forwarded to the seller's account email.

## 8. Law and wording

- FACT [R-L10] (2026-07-09): CJEU C-234/25 Sky Österreich Fernsehen, First Chamber, ECLI:EU:C:2026:556, press release 97/26: an offering "of a dynamic nature" that adapts to the user is a digital *service*, so the Art. 16(m) digital-content waiver cannot exclude withdrawal; a consumer who asked for performance to start and then withdraws pays compensation "in principle … on the basis of the period of use" or "the economic value of the content viewed". `docs/pricing.md` and `legal.ts` cite it correctly.
- FACT [R-L3] (Directive 2011/83/EU, consolidated 2018-07-01): Art. 8(7) a confirmation of the contract on a durable medium including the consumer's express consent and acknowledgement; Art. 8(8) an express request before performance in the withdrawal period; Art. 14(3) a proportionate amount for what was provided; Art. 14(4) nothing owed without the express request; Art. 16(a) no withdrawal after the service is fully performed with prior express consent and acknowledgement; Art. 16(m) digital content. Directive 2023/2673 adds Art. 11a: a "withdraw from contract here" function, continuously available and prominently displayed, applying from 2026-06-19 to any trader offering to EU consumers [R-L11]; Paddle's changelog has no entry about it.
- ESTIMATE (legal reading; two law-firm notes [R-L12]): TypePlay is a digital service under this test; the planned tick box (express request + acknowledgement + pay for use) is the right shape; the sentence "once all credits from this purchase are used, I can no longer withdraw" rests on "fully performed", which for a monthly plan with carry-over more naturally means the end of the paid month; softening it costs nothing because the refund is $0 either way once the credits are used. The law firms: avoid wording that ends the right "simply because performance begins"; the payment "must not be imposed as a lump sum or designed as a penalty".
- FACT [R-L4] (Paddle refund policy 2026-03-31): all transactions non-refundable unless the law requires; EU/EEA/CH/UK consumers have 14 days (one-off purchases and the first subscription payment, not later renewals; UK yearly subscriptions get a new 14 days at each renewal); the right is lost for digital content once used with express consent; an online withdrawal button ("Request withdrawal") sits in Paddle's customer portal for eligible transactions during the 14 days; UK consumers contact Paddle; Paddle may refund at its discretion within 14 days, weighing usage. Buyer terms (2026-03-31): the buyer contracts with Paddle under English law (US: New York).
- FACT [R-L1] (seller handbook, undated): show the terms, the refund policy and support email + phone; obtain acceptance of the terms and refund policy before purchase; the merchant-of-record sentence and the sole proprietor's name in the terms (both already in `legal.ts`); make the subscription and the amount clear; let buyers correct order errors; tell Paddle of policy changes; Paddle always sends the receipt; recommends a 30-day money-back guarantee; a clear statement descriptor; disputes above 0.75% unacceptable. One founder reports a rejection for "qualifiers" in a refund policy; Paddle sellers with usage-based rules exist (`docs/research/pricing-2026-10-16.md`).
- FACT [R-L2] (AUP 2026-04-13): prohibits "virtual currency or stored value, including but not limited to store credit, gift cards, vouchers"; nothing about prepaid credits for a service (the AI guide tells sellers to sell them).
- FACT [R-L13] (California B&P §17602, in force 2025-07-01): clear and conspicuous terms in visual proximity to the consent; express affirmative consent; an acknowledgment the consumer can retain; consent records kept 3 years or 1 year after termination; cancel online at will via a prominent link without obstructing steps; price-change notice 7-30 days before; (h) an annual reminder for "annual automatic renewal or continuous service" agreements. ESTIMATE: a monthly plan is most likely outside (h); a yearly plan is inside, and Paddle's 30-day California reminder covers it.
- FACT [R-L5]: UK: the Consumer Contracts Regulations 2013 apply today (reg. 36: express request, then a proportionate payment; reg. 37: digital content needs express consent and acknowledgement); the DMCCA 2024 subscription chapter starts January 2027 (the PM's release of 2026-08-09; the regulations are unpublished): reminders before each renewal payment that ends a six-month period, straightforward online cancellation, a 14-day initial cooling-off and renewal cooling-offs, a cooling-off notice per period; the government response (2026-04-02) keeps the digital-content waiver and gives proportionate refunds for started services. CJEU judgments after 2020 do not bind UK courts, but the UK rules give the same result.
- FACT [R-L14] (Georgia, Law 1455, in force 2022-06-01): 14 days to withdraw from distance contracts; the right ends when the service is fully delivered after the consumer's prior consent and acknowledgement. ESTIMATE: Paddle is the seller of record, so this reaches little of the buyer relationship.
